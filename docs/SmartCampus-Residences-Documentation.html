SmartCampus — Plateforme microservices

Gestion des Résidences

Documentation technique — Backend NestJS (Chambre · Demande · Contrat) & Frontend React

NestJS 10 + TypeORM + PostgreSQL Vite + React 19 + Tailwind Swagger / OpenAPI Event-driven interne

1. Contexte et périmètre

Ce document décrit le travail réalisé pour le module « Gestion des Résidences universitaires » de la plateforme SmartCampus. Le périmètre couvre :

  • Backend : une application NestJS organisée en trois modules fonctionnels jouant le rôle de microservices logiques — Chambre (socle), Demande (cycle de vie des demandes), Contrat (créé à l'approbation).
  • Frontend : les pages du module Résidences intégrées à l'application React partagée de l'équipe (routes /residences/*), branchées sur les API ci-dessus.
  • Base de données : PostgreSQL, schéma dédié BDD_Residences.
Point important : le frontend de l'équipe est une application Vite + React 19 + React Router (et non Next.js). Le module Résidences y existait sous forme de maquette 100 % mockée avec un modèle différent (résidences/lits/tickets). Il a été réécrit pour refléter le contrat réel du backend (Chambre / Demande / Contrat), tout en conservant le mode démo mocké et le design system existant (navy + violet).

2. Architecture d'ensemble

[ React (Vite) ]
      │  fetch JSON + JWT (intercepteur partagé)
      ▼
[ API Gateway / NestJS  :  http://localhost:3001/api ]
      │
      ├── Controllers ──► Services ──► Repositories TypeORM ──► PostgreSQL
      │                          │                                 schéma "BDD_Residences"
      │                          │
      │                          └── EventEmitter2 (bus interne)
      │                                 ├─ demande.approuvee  ─► ContratsService (crée le contrat)
      │                                 └─ demande.annulee    ─► ContratsService (résilie le contrat)
      │
      └── ChambresService ◄── appelé par DemandesService (occupation) et ContratsService (libération)

Les trois services partagent la même base (décision validée : « shared DB + injection de services »). Les dépendances s'expriment par injection de services NestJS et par événements de domaine, ce qui permettra une extraction en microservices HTTP indépendants sans changer les règles métier.

3.3 Règles métier et détails

  • Une chambre = un résident : deux méthodes dédiées occuper() / liberer() sont exposées au reste de l'application. occuper() réalise un UPDATE … WHERE id = ? AND disponible = true puis vérifie le nombre de lignes affectées : deux approbations concurrentes ne peuvent pas gagner. 404 si la chambre n'existe pas, 409 si elle est déjà prise.
  • Validation des DTO par class-validator (pipe global en whitelist + forbidNonWhitelisted + transform).
  • Documentation Swagger de tous les endpoints (@ApiTags, réponses typées).

4.2 Cycle de vie (transitions autorisées)

EN_ATTENTE ──► APPROUVEE   (occupe la chambre, crée le contrat, émet demande.approuvee)
EN_ATTENTE ──► REFUSEE
EN_ATTENTE ──► ANNULEE
APPROUVEE  ──► ANNULEE     (libère la chambre, résilie le contrat, émet demande.annulee)
REFUSEE / ANNULEE : états terminaux

Toute autre transition, ou une transition vers le statut courant, renvoie 409 Conflict. Une approbation exige une chambre libre (chambreId fourni dans le PATCH ou déjà souhaitée dans la demande) : la chambre est occupée de façon atomique avant l'enregistrement.

5. Backend — Phase 3 : Contrat Service

5.1 Entité Contrat

ChampTypeNotes

montantMensuelnumeric(10,2)tarif par type : SIMPLE 150 · DOUBLE 100 · STUDIO 200 TND — transformer pour exposer un nombre
statutenum, indexéACTIF | TERMINE | RESILIE

5.2 Règles métier

  • Création automatique : le service écoute demande.approuvee et crée un contrat ACTIF en récupérant le type de la chambre pour le loyer. Opération idempotente (un contrat existe déjà pour la demande → on le retourne).
  • Dates : dateFin strictement postérieure à dateDebut ; dateFin ne peut pas dépasser la fin de l'année académique (31 juillet, calculée depuis la date de début : rentrée à partir du 1er août → année suivante).
  • Résiliation : seule une résiliation d'un contrat ACTIF est acceptée (sinon 409) ; la chambre associée est libérée via ChambresService.liberer(). L'annulation d'une demande approuvée résilie aussi le contrat (écoute de demande.annulee).
  • Robustesse : les écouteurs d'événements capturent leurs erreurs et les journalisent (Logger) afin qu'un incident côté Contrat ne casse pas la réponse d'approbation de la Demande — cohérence à terme, typique d'une architecture événementielle (une réconciliation pourra être ajoutée).

6.3 PostgreSQL

  • Schéma physique dédié : BDD_Residences, créé automatiquement au démarrage (src/config/ensure-schema.ts) ou par scripts/init-schema.sql dans Docker.
  • TypeORM en synchronize: true pour le développement (piloté par DB_SYNCHRONIZE) ; les migrations pourront remplacer ce mode plus tard.
  • Un docker-compose.yml fournit Postgres 16 (base smartcampus, utilisateur postgres) — à utiliser sur une machine équipée de Docker.
  • Variables : DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME, DB_SCHEMA, DB_SYNCHRONIZE, DB_LOGGING.

7.4 Mode démo (mocks) et mode réel

L'application partagée fonctionne par défaut avec VITE_USE_MOCKS=true (les autres modules de l'équipe ne disposent pas encore de backends). Le module Résidences respecte cette architecture : chaque fonction API fournit un mock exécutant les mêmes règles (occupation atomique simulée, transitions, création/résiliation de contrat, événements toastés via le bus de démo).

Pour brancher le backend NestJS :

# .env (racine du front)
VITE_USE_MOCKS=false
VITE_API_BASE_URL=http://localhost:3001/api

8. Limites et suites

  • Authentification : le backend valide le format du Bearer token mais la vérification JWT contre le service Utilisateurs (IAuthentification) reste un stub (JwtAuthGuard + @Public()) — à activer quand le secret/JWKS partagé sera disponible. Les rôles sont pour l'instant appliqués côté front (registry) et simulés côté mocks.
  • Transactions : approbation = occupation de la chambre puis création du contrat via événement. En cas d'échec du contrat, la demande reste approuvée (log d'erreur). Une saga/outbox ou une transaction partagée (même base) pourra renforcer ce point.
  • Intégration réelle PostgreSQL : à exécuter dès que Docker ou une instance locale est disponible (création du schéma automatique au démarrage).
  • Maintenance : hors périmètre des trois services, reste mockée avec un message explicite en mode réel (501).
  • Tests front : l'application n'a pas de harnais de tests configuré ; la vérification s'appuie sur tsc + build Vite.
Résumé : 3 microservices logiques NestJS livrés et testés (Chambre, Demande, Contrat), schéma PostgreSQL dédié, Swagger, bus d'événements interne, et les 5 pages demandées du module Résidences branchées sur ces API — le tout vérifié par compilation, 36 tests unitaires, lint et build frontend.
